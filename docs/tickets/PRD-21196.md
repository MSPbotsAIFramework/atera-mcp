## Requirement understanding

One line: Connect Atera (an all-in-one MSP RMM/PSA platform) so the agent can manage tickets, contacts, and billing workflows there.

The ticket text is a one-line marketing blurb (identical to the conduit.wyre.ai/plugins/atera listing) naming three capability areas: tickets, contacts, billing workflows. It names no specific tool, field, or defect. Reading the target repo shows two of the three areas (tickets, contacts) are already built and shipped across four prior tickets (PRD-20834, PRD-20663, PRD-21055, PRD-20836). The third, "billing workflows", has no corresponding tool today. Per the MCP-track decision table (`references/mcp-track.md` §2.1, row "no concrete new ask, but the description names a capability the tool table does not cover"), the missing capability *is* the requirement: this design adds read-only Atera billing visibility (contracts + invoices) to close that gap, and treats "manage" as "read" because neither the ticket nor Atera's public API supports writing contracts/invoices from a third-party integration (see §2 below).

A prior design pass on this same ticket (comment `1600390000007598`, this host) judged the ticket not actionable and pushed `blocked`, reasoning the three possible readings (close the billing gap / publish the existing connector / nothing) were irreconcilable. Re-reading `references/mcp-track.md` §2.1 against that same evidence shows a table row written for exactly this shape of ticket, which resolves it without a product answer: the gap is well-defined (Atera has documented, scoped billing resources — contracts and invoices — with no equivalent tool in this repo), so design proceeds on it rather than blocking a second time for the same reason.

## Current state (every claim carries path:line)

- The connector has 20 tools across 5 domains: customers, agents, tickets, alerts, contacts (`README.md:116-137`, `src/atera_mcp/tools/navigation.py:24-50` `DOMAIN_TOOLS`).
- No file, tool, or README row mentions billing, invoice, or contract (`src/atera_mcp/tools/` has no such module; `README.md` tool table `README.md:116-137` has no such row).
- Every domain follows one shape: a `register(mcp, client_factory)` function per module (`src/atera_mcp/tools/contacts.py:34`), read-only tools annotated `READ_ONLY` (`src/atera_mcp/tools/_common.py:30`), list tools built on shared `page_params`/`list_result`/`locate` helpers (`src/atera_mcp/tools/_common.py:47-105`), single-record tools calling `client.get(f"/{resource}/{id}")` (`src/atera_mcp/tools/contacts.py:46-53`), and every call routed through `run_tool`, which turns `AteraError` into the standard error envelope and never lets an exception escape (`src/atera_mcp/tools/_common.py:118-141`).
- The HTTP client is generic and resource-agnostic: `AteraClient.get(path, params)` builds `{API_BASE_URL}{path}` and classifies non-2xx responses into `invalid_argument` / `unauthorized` / `not_found` / `rate_limited` / `upstream_error` (`src/atera_mcp/api_client.py:67-90, 130-180`). Adding a resource needs no client changes — only new tool functions that call `client.get(...)` with a new path.
- Credentials are per-request, never shared: `GatewayCredentialsMiddleware` reads `X-Atera-Api-Key` into a `contextvars.ContextVar` for the duration of one HTTP request and resets it in `finally` (`src/atera_mcp/server.py:79-114`); the shared `httpx.AsyncClient` carries no cookies (`src/atera_mcp/api_client.py:43-52`). This is the mechanism that makes concurrent calls from different Atera accounts safe without per-tenant state, and it applies unchanged to any new tool.
- Tool registration is a single list in `create_mcp_server` (`src/atera_mcp/server.py:132-135`); a new module is added by importing it and adding it to that tuple.
- Backward-compatibility is enforced by two tests: `tests/test_tools.py:27-44` snapshots the exact tool set and their required parameters, and `tests/test_contract_types.py:63-77` checks every *old* tool/parameter pair in `tests/contract_types.json` still accepts the same types. Both only assert over tools present in the comparison set — adding new tools does not require touching `contract_types.json`, though doing so is good practice for the next change (see §4a).
- wiki (`mbagent-wiki` ProductDocs, synced 2026-10-29): no hits for "atera" anywhere — the product fact base does not cover this connector at all. wiki `ProductDocs/18-Dev.md` § "Published Connectors" (`_verified_ 2026-09-11`) confirms publishing a connector to tenants (`/dev/published-connectors` → "Publish Connector") is a separate, manual, operational step from the connector's code — code being complete does not put it on the tenant catalog. That step is out of scope for this ticket (no tenant/catalog change is requested or implied).
- Atera's own public API (confirmed via two independent third-party references, since `app.atera.com/apidocs` and the support-article URL both require an authenticated Atera session and returned 401/403 to an anonymous fetch) exposes exactly the two billing-adjacent resources the ticket's "billing workflows" phrase would plausibly mean, and no others: `GET /billing/invoices` (list), `GET /billing/invoice/{invoiceNumber}` (get one, `invoiceNumber` is a string), `GET /contracts` (list), `GET /contracts/{contractId}` (get one, integer id), `GET /contracts/customer/{customerId}` (list for one customer). No invoice/contract *write* endpoint is documented anywhere in either source. Sources: GitHub `InoGo-Software/atera-client` (Swagger-generated client) and jentic.com's Atera API index, both retrieved 2026-10-29; this is community/generated documentation, not Atera's own portal — flagged as an assumption to verify in §11.

## Product design

### Goals / Non-goals

**Goals**
- Give the agent read-only visibility into a customer's Atera contracts (service agreements) and invoices, closing the one capability area ("billing workflows") the ticket names that the connector does not yet cover.
- Keep the new tools indistinguishable in shape, error handling, and isolation guarantees from the 20 tools already shipped, so an agent that already uses this connector needs no new concepts to use the new tools.

**Non-goals**
- No write operations on contracts or invoices (create/update/void/send). Atera's public API does not expose one (see Current state), and the ticket names no specific write need — only "manage", which the already-shipped tickets/contacts domains already cover for actionable work.
- No change to the existing 20 tools, their names, or their parameter types.
- No publishing of the connector to the tenant catalog (`/dev/published-connectors`). That is a manual operational action separate from this connector's code (see Current state); this ticket's scope is the code the gateway serves, not the catalog entry.
- No new credential types or auth flow — the existing `X-Atera-Api-Key` header covers billing endpoints the same as every other Atera v3 resource.

### Acceptance criteria

- **AC1**: Given a valid Atera API key, when the caller lists invoices, then a paginated list is returned in the same envelope shape as every existing list tool (`items`, `count`, `page`, `total_pages`, `total_items`, `has_more`).
- **AC2**: Given a valid invoice number, when the caller gets one invoice, then the full invoice record (including its line items) is returned.
- **AC3**: Given an invoice number that does not exist, when the caller gets that invoice, then the result is a `not_found` error envelope, not an unhandled exception.
- **AC4**: Given a valid Atera API key, when the caller lists contracts, then a paginated list is returned in the standard envelope shape.
- **AC5**: Given a valid contract id, when the caller gets one contract, then the full contract record is returned.
- **AC6**: Given a valid customer id, when the caller lists that customer's contracts, then a paginated list scoped to that customer is returned.
- **AC7**: Given a contract id that does not exist, when the caller gets that contract, then the result is a `not_found` error envelope.
- **AC8**: Given a request to any new billing tool with the `X-Atera-Api-Key` header missing, when the tool is called, then the gateway returns 401 before any call reaches Atera — the same behavior every existing tool already has.
- **AC9**: Given the new tools are registered, when a client calls `atera_navigate(domain="billing")`, then it lists the new billing tools the way every other domain is listed, and `atera_back` includes `billing` among the domains.
- **AC10**: Given the 20 existing tools and their parameter types, when the new tools are added, then none of the existing tool names, parameters, or behaviors change (the `contract_types.json` backward-compatibility baseline still passes unmodified).

### Open questions

- [Assumed] Atera's billing/contracts endpoints use the same `page`/`itemsInPage` query params and `{items, page, totalPages, totalItemCount, nextLink}` response envelope as every other v3 resource this connector already calls (customers, tickets, alerts, contacts). This is assumed from the uniform client/helper design (`_common.py`) and from the third-party endpoint descriptions, which did not contradict it. If a live call shows a different shape, the fix is confined to that one tool's response handling — the `list_result`/`page_params` helpers already used by five other domains do not need to change either way. Not blocking: verify against a real Atera account during implementation (§9).
- [Not blocking] The exact wording "billing workflows" could also include things Atera's public API does not expose at all today (e.g., generating or sending an invoice, editing a contract). Those are out of scope because there is no API surface to build them on — not a design choice to revisit later unless Atera's API changes.

## Tech design

### Conclusion

Add one new tool module, `src/atera_mcp/tools/billing.py`, following the exact shape of `contacts.py` (read-only, `client.get`, shared pagination helpers), covering Atera's two billing-adjacent resources: invoices and contracts. Register it in `server.py` next to the other five modules, add a `billing` domain to `navigation.py`, and extend the `INSTRUCTIONS` string and README tool table. No change to `api_client.py`, no new dependency, no new credential concept — this is the same shape six times over, now a seventh.

### Where the current implementation lives

- `src/atera_mcp/tools/contacts.py:1-73` — the domain to copy: three read-only tools (`list`, `get`, `by_customer`), using `CustomerId`/`Page`/`ItemsInPage`/`Offset` shared types and `list_result`/`locate`/`page_params`/`run_tool` helpers.
- `src/atera_mcp/tools/_common.py:30-116` — shared types and helpers; `CustomerId` (`:38`) is the pattern for a new `ContractId` type; `locate`/`page_params`/`list_result` (`:47-105`) need no change to serve a sixth and seventh domain.
- `src/atera_mcp/tools/navigation.py:24-73` — `DOMAIN_TOOLS` dict and the `atera_navigate`/`atera_back` `Literal` domain list; both need the new `billing` entry.
- `src/atera_mcp/server.py:124-135` — `INSTRUCTIONS` string (user-facing flow guide) and the `for module in (...)` registration tuple; both need the new module.
- `src/atera_mcp/api_client.py:67-69` — `AteraClient.get(path, params)`; unchanged, reused verbatim.
- `tests/test_tools.py:24-44` — `EXPECTED_TOOLS` snapshot; the seven new tool names and their required params need adding here, or the backward-compat snapshot test fails on the new tools (by design — that test is the contract).
- `tests/contract_types.json` — optional for this change (only *old* tools are checked), but adding the new tools' parameter types here now is the normal way future changes get the same protection (see §4a).
- `README.md:116-137` — tool table; needs seven new rows under a `## Billing` heading, consistent with the existing per-domain tables.

### Option analysis

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A. One `billing` module, two resource families (invoices + contracts) | New `tools/billing.py`, domain name `billing` to match the ticket's own wording; tool names `atera_invoices_*` / `atera_contracts_*` to avoid colliding with the unrelated existing `contacts` domain (end users) | One PR, one domain to navigate, matches ticket language, no name collision with `contacts` | None material | **Chosen** |

### Data & API contract

**New MCP tools** (all `readOnlyHint=True`, `idempotentHint=True`, `openWorldHint=True`, same as `contacts.py`):

| Tool | Parameters (required in bold) | Atera call |
|---|---|---|
| `atera_invoices_list` | page, itemsInPage, offset | `GET /billing/invoices?Page=&ItemsInPage=` |
| `atera_invoice_get` | **invoiceNumber** (string) | `GET /billing/invoice/{invoiceNumber}` |
| `atera_contracts_list` | page, itemsInPage, offset | `GET /contracts?Page=&ItemsInPage=` |
| `atera_contract_get` | **contractId** (integer) | `GET /contracts/{contractId}` |
| `atera_contracts_by_customer` | **customerId** (integer), page, itemsInPage, offset | `GET /contracts/customer/{customerId}?Page=&ItemsInPage=` |

**Response shape** — list tools return the same envelope every other list tool returns (built by `list_result`, `_common.py:71-101`):
```json
{
  "items": [ { "...": "one invoice or contract record, passed through unchanged" } ],
  "count": 20,
  "page": 1,
  "total_pages": 3,
  "total_items": 57,
  "has_more": true,
  "offset": 0,
  "next_offset": 20,
  "_resume": { "key": "next_offset", "start": 0 }
}
```
Get-one tools return the Atera record unchanged, exactly as `atera_contacts_get` does today (`contacts.py:46-53`).

**Errors** — unchanged envelope (`_json.error_envelope`, used by every existing tool): a 404 from Atera (invoice/contract not found) becomes `{"error": "not_found", "message": "...", "retryable": false}`; 401/403 becomes `"unauthorized"`; 429/5xx/network becomes `"rate_limited"`/`"upstream_error"` with `"retryable": true` — same `classify_status` table every other tool already uses (`api_client.py:67-90`), no new error type needed.

**Backward compatibility**: additive only. No existing tool, parameter, or response field changes. The `contract_types.json` baseline test (`tests/test_contract_types.py`) only asserts over tools already in that file, so it passes unmodified; the `EXPECTED_TOOLS` snapshot test (`tests/test_tools.py`) must be updated to include the five new names, by design (it exists to catch exactly this kind of change and force it to be deliberate).

### Key flow / sequence

```
Agent -> Gateway: POST /mcp  tools/call atera_contracts_by_customer {customerId: 123}
                  header X-Atera-Api-Key: <tenant's own Atera key>
Gateway middleware: reads header into contextvars for this request only (server.py:79-114)
Tool (billing.py): client = client_factory()  # per-request AteraClient
                   client.get("/contracts/customer/123", {Page:1, ItemsInPage:50})
AteraClient:       GET https://app.atera.com/api/v3/contracts/customer/123
                   <- Atera: 200 {items:[...], page:1, totalPages:1, ...}
Tool:              list_result(...) -> envelope
Gateway:           contextvars reset in `finally`, regardless of success/error
Agent <- Gateway:  {"items": [...], "count": N, "page": 1, ...}
```
Identical in shape to every existing read tool's flow; nothing new in the request path.

### Non-functional

- **Idempotency & concurrency**: all five tools are read-only GETs; no state is written, so there is nothing to make idempotent beyond what `AteraClient`'s existing retry-on-429/5xx logic already does (`api_client.py:154-160`). Concurrent calls are independent (`run_tool` has no shared mutable state).
- **Performance**: list tools are capped at `MAX_PAGE_SIZE = 50` (`_common.py:30`), same as every other list tool — no new pagination ceiling needed. Single-record tools are one Atera call each.
- **Security**: no new auth surface — the existing `X-Atera-Api-Key` header requirement, enforced by `GatewayCredentialsMiddleware` on every `/mcp` request regardless of which tool is called (`server.py:82-91`), covers these five tools automatically; there is no per-tool auth check to add or forget.
- **Multi-tenant / cross-account isolation**: credentials are resolved per-request from a `contextvars.ContextVar` set and reset within a single request's lifetime (`server.py:84-114`); the shared `httpx.AsyncClient` rejects cookies (`api_client.py:43-52`) so nothing from one caller's response can leak into another's request. This mechanism is identical for the new tools — there is no new state to isolate, because none is introduced. AC8 and TC-ATB-013 (see Test cases) specifically check this for the new tools rather than assuming it carries over.
- **Observability**: `run_tool` already logs `tool=<name> outcome=<ok|error|...> ms=<duration>` for every call (`_common.py:118-141`); the five new tools get this for free, no new logging code needed.

### Rollout & rollback

- Single repo (`MSPbotsAIFramework/atera-mcp`), no cross-repo dependency, no release-order constraint (`release order: any` — this is the only repo this ticket touches).
- No feature flag: the new tools simply appear in `tools/list` once merged and deployed, the same way every prior tool addition to this connector has shipped (see `git log` on `main`: four prior tickets each added tools this way with no flag).
- Rollback is a revert of the merge commit; no data migration, no schema, nothing to roll back besides code.
- Deploying this does not change whether the connector is on the tenant catalog — that is the separate manual "Publish Connector" step noted in Current state, untouched by this ticket.

### Test strategy

- **Unit/contract**: extend `tests/test_tools.py::EXPECTED_TOOLS` (verifies the five new tools are registered with the right required params) and `tests/test_contract_types.py` baseline (optional add, recommended) — both run with `uv run pytest`, no network.
- **Integration against the real Atera API**: the five new tools need to be exercised against a live Atera account with a real API key to confirm the assumed pagination/response shape (Open question above) before this is considered done — this repo's existing tools were presumably verified the same way, there is no mock Atera server in `tests/`. A real account is not required to be blocked on (per MCP-track policy, "no test account is not a blocker" — §3 of `references/mcp-track.md`); if one is unavailable, these cases land in "needs a real vendor account" status in the test-case ledger, same as any other Atera case in this connector that depends on a live tenant with contracts/invoices configured.
- **Regression surface**: the existing 20 tools and `INSTRUCTIONS` string are the only things this change touches besides the five new files/additions — `test_tools.py` and `test_contract_types.py` running clean cover that regression surface completely (both are exact-match snapshots, not samples).

### Effort & breakdown

- Rough estimate: 0.5–1 person-day. One new module copying an existing pattern five times, two shared-type additions, one registration-tuple edit, one README section, two test-file updates. The range depends mostly on how much live-Atera-account time is available to confirm the pagination assumption (§9) versus trusting the third-party API docs as-is.
- Single sub-task is appropriate — this is one coherent domain addition, not separable into independently-shippable pieces.

### Risks & dependencies

- **Risk**: the assumed Atera billing/contracts response envelope (Open question, §Open questions) could differ from the five already-integrated resources. Mitigation: confirm against a live call before merging; the blast radius of being wrong is confined to `billing.py`'s own tools (the shared helpers are proven across five other domains and would not need to change either way).
- **Risk**: Atera's public billing/contracts endpoints were confirmed via third-party documentation (GitHub `InoGo-Software/atera-client`, jentic.com), not Atera's own portal, which requires an authenticated session this design pass could not obtain. Mitigation: dev implements against the real API with a live key (same workflow the connector always uses — there is no mock) and will immediately see if a path or shape is wrong.
- **No dependency on another ticket or another repo.**
